## Overview

**DON'T FEED THE MONSTER** is a browser-based, first-person horror game set in an underground research facility. Explore the environment, locate important objects, solve the containment objective, and avoid **Subject 09**—a creature that reacts to player movement, sound and visibility.

The project is built with **TypeScript, Three.js and Vite**. Its code is separated into application lifecycle, player, monster AI, world, gameplay, UI, rendering, chapter configuration and testing modules.

> **Project status:** This repository contains a playable Chapter 1 foundation and supporting systems/configuration for a wider chapter-based campaign. Chapter metadata and AI profiles for later chapters are present, but the current bootstrap starts Chapter 1. Do not assume every planned chapter is playable yet.

## Gameplay

### Player

- First-person camera and mouse-look.
- WASD movement with sprinting and crouching.
- Collision-aware movement through the facility.
- Flashlight and interaction controls.
- Noise events generated by movement and distractions.

### Subject 09

The monster logic is split into dedicated systems for state, perception, navigation, memory and presentation.

| Behaviour state | Purpose |
|---|---|
| `PATROL` | Follows its patrol behaviour. |
| `INVESTIGATE` | Responds to a suspicious sound or event. |
| `SEARCH` | Searches around a last-known or suspected player position. |
| `CHASE` | Pursues the player after detection. |
| `RETURN` | Returns towards its configured behaviour or location. |

Perception and navigation are implemented as game logic; the monster is **rule-based AI, not machine learning**.

### Facility and objectives

The world modules define the facility layout, collision data, geometry, lighting and navigation graph. Chapter 1 includes an objective-driven experience with keycard/exit progression, interactable objects and hiding mechanics.

## Architecture

The source is organised by responsibility. The following is the project structure represented by the supplied source dump:

```text
src/
├── app/          # Application lifecycle, bootstrap, config, services and game loop
├── chapters/     # Campaign index, chapter definitions and per-chapter AI profiles
├── core/         # Shared types, events, state machine, logging, random and disposal
├── gameplay/     # Hiding, distraction, objectives, sound events and restart systems
├── input/        # Input bindings, keyboard/mouse input and pointer lock
├── monster/      # Subject 09 state, perception, memory, model and navigation
├── player/       # Player controller, motor, collider, camera, flashlight and noise
├── rendering/    # Renderer, lighting and audio manager
├── save/         # Save-management boundary
├── testing/      # AI harness, gameplay assertions and test scenarios
├── ui/           # Menus, HUD, prompts, settings and chapter screens
├── world/        # Facility construction, layout, collision and navigation
├── main.ts       # Browser entry point
└── style.css     # Global application styles
```

### Runtime composition

```text
main.ts
  └── GameApplication
        ├── GameBootstrap
        │     └── GameServices
        │           ├── EventBus + GameStateMachine
        │           ├── RendererManager + WorldManager
        │           ├── PlayerController + Flashlight
        │           ├── Subject09
        │           ├── GameUI
        │           └── GameLoop
        └── GameController
              └── Coordinates gameplay updates and state transitions
```

### Key module responsibilities

| Module | Responsibility |
|---|---|
| `app/GameApplication.ts` | Creates, starts and disposes the application. |
| `app/GameBootstrap.ts` | Constructs runtime services in dependency order. |
| `app/GameServices.ts` | Defines the shared runtime service contract. |
| `app/GameController.ts` | Coordinates game state, input and gameplay systems. |
| `app/GameLoop.ts` | Owns the animation loop and bounded simulation steps. |
| `core/EventBus.ts` | Typed event communication between systems. |
| `core/GameStateMachine.ts` | Controls valid game-mode transitions. |
| `core/Disposable.ts` | Centralises cleanup of listeners and resources. |
| `player/` | Player movement, camera, collision, flashlight and noise. |
| `monster/` | Subject 09 AI state, perception, memory and navigation. |
| `world/` | Facility layout, geometry, lighting, collision and paths. |
| `gameplay/` | Interactions and reusable gameplay mechanics. |
| `chapters/` | Campaign metadata and chapter-specific AI configuration. |
| `ui/` | Menus, HUD, prompts, journal-like and chapter UI components. |
| `testing/` | Headless checks and gameplay assertions. |

See [`ARCHITECTURE.md`](ARCHITECTURE.md) for the expanded architecture notes.

## Run locally

### 1. Clone

```bash
git clone https://github.com/Iamjustadityagupta/dont-feed-the-monster.git
cd dont-feed-the-monster
```

### 2. Install dependencies

```bash
npm install
```

### 3. Start the development server

```bash
npm run dev
```

Open the local URL printed by Vite (usually `http://localhost:5173`).

### 4. Validate and build

```bash
npm run typecheck
npm run build
```

The production bundle is written to `dist/`.

### Other scripts

```bash
npm test
npm run test:reach
npm run preview
```

- `npm test` runs the headless test scenarios.
- `npm run test:reach` runs the gameplay reachability assertions.
- `npm run preview` serves the production build locally.

## Development workflow

1. Create a feature branch.
2. Make a focused change in the relevant system.
3. Run `npm run typecheck`.
4. Run the relevant tests and `npm run build`.
5. Test the game in a browser—especially pointer lock, movement, collision, UI and audio.
6. Commit and push the change.
7. Deploy through the RUN.game workflow and verify the resulting release status.

A successful GitHub push does **not** automatically publish a new RUN.game build.

## Known scope and limitations

- Chapter 1 is the current runtime starting point; later chapter files provide campaign definitions/configuration and should not be described as completed playable chapters without further implementation and testing.
- Subject 09 uses deterministic/rule-based gameplay logic, not a trained ML model.
- Visual quality, input feel, audio playback and browser compatibility require manual browser testing in addition to automated checks.
- The game uses Three.js; it is not built on a full physics engine.
- No license is declared in this repository. Until a license is added, do not assume others have permission to reuse or redistribute the code.
